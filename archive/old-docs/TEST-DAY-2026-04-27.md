## eReader (Boox)

### B1 — Position sync opened wrong book + wrong chapter
**Symptom:** Last reading was Isaiah (Bible). On reopen, eReader landed on Genesis 39 — hadn't been there in weeks.

**Hypothesis (most likely root causes, ranked):**
1. **Stale Bible per-book position winning the merge.** The recent visibility-handler rewrite (Apr 25) only adopts cloud when chapter differs *and* cloud is materially ahead. If the eReader's local Bible position was Genesis 39 (cached from weeks ago) and cloud had Isaiah, that should have triggered "chapter differs → adopt cloud." If it didn't, either (a) cloud Bible position was never written from the device where Isaiah was read (Apr 23 regression — `tinct-current-book` removal — could have left Bible position uncupserted), or (b) cloud Bible row's `updated_at` was older than the Genesis-39-era local because Isaiah reads went only to local on the other device.
2. **Cross-book index bleed.** Anders's intuition: maybe a chapter index from another book (chapter 39 of *something*) got applied to Bible. Worth checking: is there a single position store keyed only by chapter index, with bookId resolved later?
3. **`tinct-current-book` pointer was stale.** Apr 23 regression removed the write; restored Apr 25. If eReader hadn't done a `handleBookChange` since the fix shipped, current-book may have pointed to Bible while the actual chapter pointer was last-good-Genesis.

**Fix sketch:** On eReader, open DevTools → inspect `window.__tinctPositionDebug` and `window.__tinctSupabaseDebug` after reproducing. Query Supabase `reading_positions` for Bible — count rows, check `updated_at`. Add a hard rule: when local position's `updatedAt` is >24h older than cloud, always adopt cloud regardless of chapter-mismatch test.

### B2 — Library "remove book" icon invisible on eReader
**Symptom:** On desktop/mobile, library has a remove icon. On eReader, no icon visible (function may still work blind, but no affordance).

**Hypothesis:** CSS `:hover`-only reveal (icon shown on hover, hidden by default) — doesn't trigger on e-ink touch. Less likely: SVG color/opacity that doesn't render under e-ink mode.

**Fix sketch:** Make remove icon always-visible on touch devices (or all devices). Audit any other `:hover`-only affordances in the library/feed UIs.

### B3 — Chat intermittent on eReader
**Symptom:** "Writing…" indicator appears, but response never arrives. More flaky than desktop/mobile. Reproduces sometimes, not always.

**Hypothesis:** Boox's modified Chromium handles streaming SSE / `fetch` with `ReadableStream` poorly, especially when the device aggressively sleeps network sockets. The optimistic "writing" placeholder is added on send, replaced by streamed tokens — if the stream errors silently, placeholder is never replaced.

**Fix sketch:** Add a 30s timeout on chat streaming with visible error state ("Connection dropped — retry?"). Add a `[chat]` error counter to a `window.__tinctChatDebug` for diagnosis. If isolated to eReader user-agents, fall back to non-streaming JSON response there.

### B4 — Audiobook fails on book content (AI audio works)
**Symptom:** Companion/AI audio plays reliably. Pre-generated book audio fails to play.

**Hypothesis:** AI audio likely uses a different path (client-side TTS blob or different endpoint). Book audio comes from R2 via `/api/audio-file` proxy with range requests + recent rate-limiting (Apr 21 anti-scrape). Boox's audio stack may fail on (a) range requests, (b) specific MP3 encoding the proxy passes through, or (c) the rate-limiter cutting off slow chunked fetches.

**Fix sketch:** Reproduce on eReader with DevTools → Network tab open. Check actual response: 200 partial / 416 / timeout / 429? If 429, eReader may be tripping the 30-req/60s limit on chunked fetches — needs higher limit for `/api/audio-file` or different keying.

### B5 — Play button shape: oval, not circular
**Symptom:** Play button looks taller than wide on eReader.

**Hypothesis:** CSS missing `aspect-ratio: 1` or asymmetric padding, or width/height set in different units (em vs px) that compute differently with eReader's font metrics.

**Fix sketch:** Force `width: Xpx; height: Xpx; aspect-ratio: 1; padding: 0` on the button, center the icon explicitly.

### B6 — Full-screen mode has no exit affordance
**Symptom:** Tapped full-screen, worked once, then went blank. Top menu now hidden, no visible exit. Trapped.

**Hypothesis:** Full-screen mode hides chrome (including the toggle that exits it), assuming a gesture or hardware key handles exit. eReader has no such binding.

**Fix sketch:** Always-visible small ✕ in a corner while in full-screen. As secondary affordance, a tap on empty margin re-shows top bar for 3s.

## Onboarding

### B10 — Book onboarding doesn't fire when adding a book to the library
**Symptom:** Added a new book to the library, was taken straight into the reader. Book Onboarding modal (edition picker → angle → cast) never showed. Per CLAUDE.md the modal is meant to fire for ALL entry points — this is a regression of a hard rule.

**Hypothesis (ranked):**
1. **Stale onboarding-completed flag from prior remove/re-add.** If Anders had this book in the library before and removed it, the per-book "onboarding completed" state in localStorage was probably never cleared on remove. Re-adding finds the flag still set → skips the modal. This would also explain why first-time-add works for books you've never had but breaks for previously-removed ones.
2. **Library "add" flow opens the reader without the onboarding gate.** Deep-link/SEO entry routes through the gate; "add to library → open" may bypass it.
3. **Onboarding state keyed at the wrong scope** (e.g. per-session global "has seen onboarding once" instead of per-book).

**Fix sketch (and product-spec follow-ons from Anders):**

- **Always fire onboarding on new-to-library books.** Before opening a book after add, check per-book onboarding-completed flag. If unset → show modal.
- **Re-add prompt for previously-removed books.** If the book was in the library before and removed, show: *"You've read this before. Use your previous reading angle and editions, or start fresh?"* Two buttons: **Keep previous** / **New onboarding**. Requires not deleting onboarding state on remove (just mark as "removed" with state preserved).
- **Carry forward last-used edition preferences as defaults.** When the onboarding modal opens for a new book, pre-select primary edition / secondary edition / audiobook edition from the user's most-recent picks (e.g. if last book had modern-en as primary, default this book's primary to modern-en too). User can always change. Store at `tinct.account.lastEditionPrefs` so it syncs across devices (per the B9 split — these are content preferences, not layout).

**Implementation notes:**
- Removing a book ≠ deleting all per-book state. Keep `onboarding-state:{bookId}` and `reading-position:{bookId}` etc., just remove from "active library" list.
- The "last-used edition prefs" default should kick in *only when* the user has previously made a choice — for the very first book ever, fall back to whatever the current default is.

## Audio playback

### B12 — Audio speed resets on pause/play, UI label stays at chosen speed
**Symptom:** Pick 1.5x → audio plays at 1.5x ✓. Pause → press play → audio plays at 1.0x but the speed indicator still says "1.5x". Toggling through the speed control restores 1.5x.

**Hypothesis:** Speed is stored in React state, but `<audio>.playbackRate` is only set when the speed control is interacted with — not reapplied when the audio element starts playing again after a pause (or remounts). The DOM `<audio>` element resets to default `playbackRate = 1.0` on certain transitions; the React state holding "1.5" doesn't auto-sync back to the DOM property. Display label reads from React state → looks correct but is lying.

**Fix sketch:**
- On every `play` event of the `<audio>` element, set `audio.playbackRate = audioSpeed` from state. (Cheap idempotent guard.)
- Persist `audioSpeed` as a **synced** preference (`tinct.account.audioSpeed` per B9 split — this is a content-experience choice, not device layout). Default 1.0.
- On audio element mount and on chapter change, apply persisted speed before/at first play.
- Verify across pause/play, chapter advance, and page navigation.

### B19 — Position resets to chapter 1 after the subscription gate
**Symptom:** Boox was at chapter 5 of The Awakening. Hit subscription gate. Dismissed back into Tinct. Now at chapter 1 of The Awakening. The bad chapter-1 position then propagated to desktop (which had been at chapter 5 too).

**Hypothesis (most concerning of the cluster):** Something in the subscription-gate flow is *writing* a position. Either:
- The TierChooser / subscription modal mounts before the user's saved position is loaded, renders the reader at default (chapter 1, page 0), and a `saveNow` heartbeat fires from that render → overwrites cloud with chapter 1.
- An auth/session refresh during the gate is treated as a "new session" and resets the in-memory position before the cloud value is fetched.

Bad chapter-1 writes from one device wipe out chapter-5 reads from another. This is the kind of bug Anders flagged as "the worst UX failure a reader app can have" in the core principles.

## Position sync — consolidated root cause analysis

All position-sync findings (B1, B15, B16, B17, B19) cluster around a single architecture issue: **the system has 3 sources of truth (local cache, cloud, in-memory React state) with merge rules that are inconsistent across the load/save/refresh paths.**

The Apr 25 hardening fixed several specific holes (heartbeat, retry, visibility-handler cloud-wins rule, current-book write restoration) but didn't address the systemic issue: **any code path that mounts the reader at a default position before cloud has loaded can poison cloud with that default if the heartbeat/visibility handler fires before cloud arrives.** B19 is exactly this pattern.

**Suggested fix architecture (for after testing day):**
1. **Block reader render on cloud read.** Show a 500ms loading state on first mount; only render the reader once cloud has resolved (with timeout fallback to local). No "render-default-then-correct" path.
2. **Disable position writes while subscription/auth/onboarding modals are open.** Treat these as "non-reading" states.
3. **Strict write rule:** never write a position whose `updatedAt` is older than the user's last in-memory read position. If we just rendered chapter 5 from cloud, never overwrite cloud with chapter 1 from default-state.
4. **Add an in-app debug page** that surfaces all 3 layers (local localStorage, in-memory state, cloud Supabase row) side-by-side per book, with timestamps. Lets you diagnose any future divergence in seconds.

## Audio playback

### B14 — Audio speed drifts upward during playback; "2x" plays slower than expected
**Symptom:** While listening normally, the speed climbed on its own — past where Anders had set it, up to the 2x display label. At 2x the audio sounded *slower* than it should at true 2.0x rate. So the displayed speed and actual `playbackRate` are out of sync, and the displayed value is drifting upward.

**Hypothesis (shared with B12 — same root cause likely):** The audio speed system has two sources of truth that diverge:
1. **React state / UI label** — the "1.5x", "2x" indicator. This drifts upward (some event is incrementing it without user action).
2. **DOM `<audio>.playbackRate`** — the actual played rate. This stays lower because either (a) it's not being reapplied when state changes, or (b) it's being clamped, or (c) it's compounding off a stale value.

Likely culprits for the upward drift:
- A keystroke/tap event firing the "speed up" handler unintentionally (e.g., a button overlapping a tap target the user actually wanted, or a keyboard handler firing on chapter advance).
- An effect that re-runs on chapter advance / page change and *increments* the speed each time instead of *applying* it (e.g., `setSpeed(s => s + 0.25)` instead of `setSpeed(0.25)`).
- A multiplier bug: `audio.playbackRate = base * userSpeed` where `base` is also user speed → compounding (1.5 × 1.5 = 2.25, but UI clamps display to "2x"; meanwhile the audio element itself caps at some lower value, hence "2x sounds slow").

**Fix sketch (combine with B12):**
- Single source of truth: persisted `audioSpeed` in `tinct.account.audioSpeed` (synced).
- One effect: `useEffect(() => { audio.playbackRate = audioSpeed }, [audioSpeed, audio])` — set, not multiply.
- Speed control handlers should *set* the new value, never increment from current.
- On every `play` event of the audio element, reapply: `audio.playbackRate = audioSpeed`.
- Add a small debug overlay in dev mode showing `displayed=X actual=Y` so future drift is visible.
- Audit any handler that touches speed for unintended triggers (chapter advance, page navigation, keyboard, etc.).

### B13 — Pagination misaligned by ~1 column on panel toggle (single AND split view)
**Symptom:** A sliver of the *previous* page bleeds in on the left edge of the reader — visible as 1-2-word-wide text fragments in the gutter to the left of the main column. Reproduces in:
- **Single-pane** after closing the side panel (`Screenshot 2026-04-27 at 10.08.46.png` — visible sliver "all, and thrust his maids to the wall." on the left edge)
- **Split-pane** with both editions visible (`Screenshot 2026-04-27 at 10.09.18.png` — Danish fragments "Så hvis…", "…vertage over", "…skabbet til" stacked vertically on the left edge)
- **Originally observed** with side panel open: `Screenshot 2026-04-27 at 10.07.45.png` (middle column truncated on right)

Switching app focus to Ghosty terminal and back triggers a browser layout pass that re-snaps the columns cleanly. So the underlying content/pagination is correct — only the *display offset* is wrong.

**Hypothesis (sharpened by the new screenshots):**
This looks like a **page-offset translate that's stale** rather than just unmeasured columns. The reader uses CSS multi-column with a `transform: translateX(-pageWidth * pageIndex)` (or equivalent) to flip pages. When the container width changes (panel toggle, split-pane toggle), the transform is computed against the *old* width, so the snap is off by the width-delta — leaving the previous page partially visible on the left. The `overflow: hidden` clip should hide it but is either missing on this state, or the transform is applied to an element wider than its clip. A browser-level reflow (Ghosty refocus) recomputes the transform from current measurements.

Alternative: pagination JS recomputes column count correctly but doesn't update the `currentPage * pageWidth` offset, so the page index is right but the pixel translate is wrong.

**Fix sketch:**
- After any panel-toggle or split-pane-toggle: `requestAnimationFrame(() => recalcPagination())` once the CSS transition settles (`transitionend` event on the panel container).
- Better: `ResizeObserver` on the reader inner container — on width change, recompute both the column layout *and* the current page transform offset.
- Audit: any place that stores `pageWidth` in a ref or state and uses it for transform — must be recomputed on container width change, not just on `window.resize`.
- Verify reproduction in both pane modes after fix; do a rapid panel-toggle stress (10× in 5s) — final state must be clean.

### B25 — "Something went wrong / Refresh page" error messages persisted in chat history
**Symptom:** Anders saw seven copies of `Something went wrong. If this keeps happening, a page refresh usually fixes it. Refresh page` stacked in one conversation. These are transient UI errors, not real assistant turns — they shouldn't be in the persisted transcript.

**Root cause:** `useClaude.ts` line 167-174 — on Claude API failure, an error message with `refreshAction: true` is added to the in-memory message list. The chat recorder effect in App.tsx then persists the latest assistant message to chat-history storage without filtering for the `refreshAction` flag. Every API failure across sessions accumulated.

**Fix (shipped 2026-04-27):**
- Recorder filters `refreshAction === true` (defense at write time)
- Per-book + global cleanup loops strip existing pollution (filter at load time, rewrite storage when dirty)

### B24 — Reading angle leaks across books
**Symptom:** Anders opened Plato's Apology without going through book onboarding (because B10 isn't fixed yet — onboarding doesn't fire on add). In the chat, the reading angle showed The Awakening's angle ("Chopin presents the Romantic conflict...") instead of being blank or Apology-specific.

**Hypothesis:** Reading angle is stored as a global setting (one slot for "current angle") rather than keyed per-book. When user sets an angle for book A, then opens book B, the chat's system prompt still injects book A's angle. Same shape as B1 (cross-book leak) but for the angle field.

**Fix sketch:** Reading angle must be keyed by `bookId`. Either store under `reading-angle:{bookId}` or as a property of the per-book onboarding state object. On chat initialization, look up angle for the current book — if none, blank, no fallback to another book. Defense in depth: when book changes (the bookId-change effect), explicitly clear any in-memory angle from previous book.



### B21 — Cross-book page-index bleed (sibling of B1)
**Symptom:** Two brand-new books (Peloponnesian War, Apology) both opened on desktop at chapter 1, **page 19 of 21**. Identical position on books that had never been opened. Mobile opened the same books at page 1 with onboarding firing — suggests the issue is desktop-specific stale state, OR a non-deterministic write that landed the same value on both.

**Hypothesis:** Phase 1's bookId-change effect resets `currentPage` to 0 and `setReaderKey++` to remount Reader, but the Reader component may compute initial page from `scrollFraction` in `savedPos.current` or another shared ref. If a previous book wrote page 19 and the savedPos ref carries over (or scrollFraction is shared), the new book picks up a non-zero initial page despite the explicit reset.

**Diagnostic to run:** Console on desktop:
```js
localStorage.getItem('position:peloponnesian-war')
localStorage.getItem('position:apology')
window.__tinctPositionDebug
```

**Fix sketch:** Audit every place that consumes `savedPos.current` or scrollFraction during initial render — they must clear/skip when bookId just changed. May need a `pendingBookSwitch` flag in App.tsx that suppresses scrollFraction-based page restoration for one render after a book change.

### B23 — Boox browser renders desktop layout but viewport is too narrow

- Or: explicitly tune a Boox layout that's neither pure desktop nor pure mobile (single-column with readable font, no split-pane by default, no narrow side panels)
